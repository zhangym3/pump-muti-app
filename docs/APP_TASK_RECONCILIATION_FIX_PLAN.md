# APP 任务结果对账锁修复方案

状态：APP 修复已实施并更新安装至手机，本方案验收测试全部通过：124 项单元测试、3 项真机页面测试、1 项真实 BLE 连接与重连测试，以及 Debug 和 Android 测试 APK 构建。只读验收确认启动对账锁解除、主机水泵输出关闭，手机账本与历史未被改写。详见 [验收记录](APP_TASK_RECONCILIATION_ACCEPTANCE.md)。本次不包含固件修改、设备重启、刷写或泵阀控制操作。

## 问题现象

重新连接主机后，出水页显示“暂不可启动：上一次请求尚未结束或流量、节点结果仍在对账”，即使上一次任务已经完成且手机本地保存了完整结果。

现场手机本地记录中的任务为 `client=d82ef12190ff6359`、`seq=1`、主机启动标识 `epoch=15`、任务 `job=15:6`，目标为槽位 1 的 500 mL。保存的结果为：

- 主机报告：`phase=6`、`done=1`、`failed=0`、`unknown=0`。
- 计量汇总：`total_ml=502`，槽位 1 已计量。
- 从机 FLOW：地址 `3`、`pulses=2957`、`ml=502`、`phase=DONE`、`terminal=1`、`measured=1`、原因 `TARGET`。

## 原因

APP 重连时从控制账本恢复已完成的任务，并从历史记录恢复节点地址；同时将当前 UI 状态中的 `report`、`volume` 和 `flows` 清空。启动完整性检查只读取当前 UI 状态，没有使用已经加载的匹配历史结果。因此 `taskResultsComplete` 返回 `false`，`taskNeedsReconciliation` 保持 `true`，启动持续被拦截。

APP 会周期性查询原任务。若主机已经不再保留该任务并回复 `UNKNOWN`，该回复不能补齐结果；手机已有的完整历史仍未被恢复到当前状态，锁定就会持续。现场 Android 日志能确认 GATT 写入成功，但不记录协议响应正文，所以本方案不把当前 `UNKNOWN` 回包视为本次现场日志已独立复核的事实。

相关代码位置：

- `app/src/main/java/com/cczb/app/MasterControlViewModel.kt`：`taskResultsComplete`、`taskReconciliationDetails`、`taskNeedsReconciliation`、`connect()`、`startBlockReason`。
- `app/src/main/java/com/cczb/app/MasterHistory.kt`：手机本地任务历史的读写和字段校验。
- `app/src/main/java/com/cczb/app/MasterProtocol.kt`：任务身份、任务编号和结果消息结构。

## 修复目标与范围

1. 重连后按完整任务身份恢复匹配的本地结果，使已完整对账的历史任务不再造成永久启动锁。
2. 保留现有防重启和结果安全门槛。仅凭账本中的 `FINISHED` 不足以解锁。
3. 历史缺项、任务身份不匹配、节点地址不匹配、结果含未知节点或结果未终结时，继续拦截启动并显示具体缺项。
4. 只改 APP，不改变 GATT/Mesh 命令格式、固件任务逻辑或历史文件格式；不得清理用户已有任务记录。

## 推荐实现

### 1. 查找匹配历史

在 `connect(device)` 恢复任务时，同时查找该主机对应的 `MasterHistoryEntry`。查找必须至少匹配主机 BLE 地址、`client`、`seq`；命中的历史还必须满足：

- 历史任务的 `epoch` 与恢复任务一致；
- 历史任务 `job` 与账本任务 `job` 一致，且 `job.epoch` 与任务 `epoch` 一致；
- 任务 mask 一致；
- 历史节点槽位与任务 mask 对应，节点地址唯一且有效。

不允许用同一主机上另一任务、另一主机、另一客户端或另一启动 epoch 的结果解锁当前任务。

### 2. 恢复结果状态

找到匹配历史后，把 `report`、`volume`、`flows` 和节点地址一起恢复进当前 UI 状态。完整性判断继续使用现有安全标准，并对所有字段校验任务关联：

- 主机报告与任务的 client、seq、job、mask 匹配，且已到终态；
- `unknown` 为零，所有被选槽位均有终态结果；
- 汇总量覆盖全部被选槽位；
- 每个被选节点都有该 job 的终态且已计量 FLOW；
- 预期节点地址完整且与槽位映射一致。

若完整性检查通过，`taskNeedsReconciliation` 自然变为 `false`，启动入口按其他现有状态门槛继续判断。不要通过直接清空 `task`、强制改为可启动或忽略结果字段来解除锁定。

### 3. 处理后续主机查询

当当前任务已由完整、身份匹配的本地历史恢复时，主机查询返回 `UNKNOWN` 不应覆盖或降级本地已确认的完整结果。查询得到匹配任务的有效终态报告时，仍按现有合并规则处理并持久化更新。

若本地结果不完整，继续查询原任务，并保留拦截。查询失败或 `UNKNOWN` 只能更新诊断提示，不能自动把未完成任务标成成功，也不能创建或重发一个新任务。

### 4. 明确阻塞原因

对账详情应指出缺少的部分，例如匹配主机报告、计量汇总、节点 FLOW、节点地址映射或终态确认。完整历史恢复成功时显示“已恢复本机保存的完整结果”，避免用户将其误认为水泵或 Mesh 故障。

## 验收测试

### 单元测试

1. 完整历史在重连恢复后还原 R/V/FLOW 和节点映射，任务结果完整，且在其它主机安全状态就绪时允许开始新任务。
2. 相同 `seq` 但主机地址、client、epoch、job 或 mask 不同的历史不能用于解锁。
3. 分别缺少 R、V、FLOW 或节点映射时仍阻止启动，并给出对应缺项。
4. 报告未到终态、含 `unknown`、FLOW 未终结或未计量时仍阻止启动。
5. 完整本地历史恢复后收到主机 `UNKNOWN`，结果仍保持完整；不完整历史收到 `UNKNOWN` 仍保持拦截。
6. 没有历史记录时，保持现有查询与对账行为；`PENDING` 或 `ACCEPTED` 任务不会被当作已完成。
7. 任务历史 Properties 的读取、写入格式保持兼容，测试不得通过清空历史或控制账本制造可启动状态。

### APP 与现场验收

- 执行 APP 单元测试、Debug 构建及现有 Android 测试源码编译。
- 使用本次现场任务的历史数据进行重连恢复回归，确认启动锁解除且任务详情仍显示原有 502 mL、2957 脉冲及完成原因。
- 使用人为构造的缺 FLOW 和错 job 数据验证启动仍被拦截。
- 真机验收期间只验证状态同步和 UI 门槛，不发送启动/试泵命令；确认主机输出关闭后结束验收。

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 错用其它任务或主机的历史数据 | 使用主机地址及完整任务身份严格匹配，并校验节点槽位映射 |
| 历史文件损坏或字段缺失 | 维持 `historyHealthy` 检查；不完整记录不解锁，不删除原文件 |
| 主机查询响应覆盖完整历史 | 对非 OK/UNKNOWN 响应不降级已匹配的完整终态结果 |
| 恢复历史后把旧结果误作实时状态 | 恢复的 FLOW 只用于任务结算与完整性判断；不得将旧 `receivedAt` 当作实时流量显示 |
| 本地历史与固件状态不一致 | 仅对严格匹配且完整的已持久化终态结果解锁；仍刷新主机输出、故障、从机清单等当前安全状态 |

## 实施边界

这是 APP 本地恢复逻辑修复，不要求主机或从机升级，也不需要重置 Mesh、重启主机或重启泵阀。实现后先跑自动化测试，再用本地历史记录做只读重连验收；实际出水测试另行安排并须明确授权。
